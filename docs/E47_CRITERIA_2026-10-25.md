# E47 criteria (FROZEN 2026-10-25, before any E47 row is generated)

## Question

E46 (result a73f77d) upscaled every image to a longest side of 1,024 px
before the processor. That made the printed total readable where the digits
questions looked: on bind dev the second digit went from 0.30 / 0.37 to
0.88 / 0.79. The synthetic field_threshold test moved less, from
0.635 / 0.620 to 0.677 / 0.692, under the 0.70 gate. That family has a
median relative gap of 2.4 % and 37 % of its rows under 1 % (E38a train),
which needs digits beyond the second. The E45/E46 digits family asks only
the first digit, the second digit and the digit count.

**E47 asks whether asking for every digit position of the printed total
(cents included) closes the fine-gap comparison, starting from the E46
checkpoints, with the E46 input rule and nothing else changed.**

The goal side is unchanged. In E46 a higher goal weight moved the swap
accuracy in opposite directions on the two seeds (+4.0 / −4.3 pp), so E47
does not change it. G2 is read as measured.

## Arm (one arm, two seeds)

- Init: the E46 U1024 checkpoints (s42 `724b81b8…`, s43 `16900445…`), read
  from the output of kernel `gjusev/mkshv-e46a-train`, sha-verified.
- Input rule: E46 U1024 (upscale to and cap at 1,024 px), in training and in
  every evaluation.
- Recipe, slots, optimiser, selection key, steps (800), dev cadence (200) and
  bind weights: exactly E46 (num_syn 0.20, num_cord 0.10, cmp_text 0.05,
  digits 0.20, range 0.05, goal 0.20, goal_match 0.20).
- Train deadline 2.5 h, wall kill 3.2 h (E46 U1024 needed 2.94 h wall).
  Workers set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, because E46
  peaked at 14.3 GB reserved of 14.56 GB. This changes allocation only, not
  the computation.

## Bind pool v3 (generated by `scripts/gen_e47.py` after this commit)

Every E45 bind row is kept unchanged except the `digits` kind, which is
regenerated on the same images (E38a field_threshold and E41 CORD, train and
dev, probe documents and their siblings still excluded). One question per
image, drawn deterministically from the row id:

- with probability 1/4, the number of digits of the whole-number part
  (options 1–7, as in E45);
- otherwise digit position k, uniform over the positions of the printed
  total with separators and the decimal point removed (EUR keeps two
  decimals, IDR has none). "What is digit k of the total on this document,
  counting from the left and ignoring separators?", options 0–9 (1–9 for
  k = 1).

Rows are grouped two per slot as in E45. Dev rows (selection only) follow the
same construction on dev images.

## Measurements

Same as E44–E46 (M1 probe, M2 E38a field_threshold test, M3 E43 swap + own
goal, M4 E38c CORD, N1 synthetic test non-FR, N2 E38c GUI, N3 testC / task),
with the U1024 rule everywhere (`scripts/e43_infer.py --upscale 1024`).
Reported without a gate: bind dev by kind and by gap bucket, digits dev by
position, probe O and T.

## Success rules (thresholds unchanged)

- **G1 numbers**: both seeds: probe SYN S ≥ 0.50, L and H ≥ 0.90, and
  M2 ≥ 0.70.
- **G2 goals**: both seeds: M3 swap ≥ 0.80 and own goal ≥ 0.80.
- **G3 no regression against the released E41 checkpoint of the same seed**:
  N1 drop ≤ 2.0 pp, N2 drop ≤ 3.0 pp, N3 drops ≤ 3.0 pp each. New in E47:
  the E41 reference values are computed from the E41 per-case eval files
  (exact counts), not from rounded constants, so a boundary case like E46's
  3.03 pp cannot be decided by rounding.

G1 + G3 or G2 + G3 make that capability a release candidate, pending a
recalibration experiment (E42 protocol, new criteria) that also fixes the
input rule in the inference contract. A release would also need its headline
numbers confirmed on fresh sets, because M2 and M3 have now been read as
gates in E44, E45, E46 and E47. E47 changes no public number by itself.
